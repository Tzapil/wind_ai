# Попутного ветра — инструкции для агента-разработчика

Браузерная 2D-игра о торговле и плаваниях в Средиземном море около 1550 года, по мотивам ранней Voyage Century Online. TypeScript, Vite, Phaser 4, Preact; ядро симуляции — чистый TypeScript в Web Worker, позже оно же станет сервером. Публичный репозиторий, лицензия MIT. Автор проекта не пишет код каждый день: он ставит задачи, смотрит итоги вех и принимает решения по игре. **С автором общайся по-русски.**

## Одна сессия — одна задача

Каждая сессия начинается с чистого контекста и выполняет **ровно одну задачу**. Память между сессиями — файлы в репозитории, а не история чата:

1. Прочитай **`docs/progress.md`**: текущая веха, статусы задач, заметки прошлой сессии, «Ждёт автора».
2. Если `Состояние` не `continue` — ничего не делай, коротко перескажи автору, чего ждёшь (раздел «Ждёт автора»), и закончи.
3. Возьми первую незаблокированную задачу со статусом `todo` (или продолжи `in progress`).
4. Прочитай её описание в ТЗ этапа и только нужные разделы документов (карта ниже). Документы целиком читать не нужно.
5. Выполни задачу по циклу ниже и **закончи сессию**. Следующую задачу возьмёт новая сессия.

Исключение — задачи объёма S, идущие подряд в одной вехе: можно сделать две в одной сессии, если контекст ещё свободен. Задачи объёма L и XL, наоборот, можно делить на несколько сессий: прогресс внутри задачи — в заметке к ней в `docs/progress.md`.

## Цикл задачи

1. Отметь задачу в `docs/progress.md` как `in progress`.
2. Создай ветку `t-23-ship-movement` от свежего `main`.
3. Сделай задачу полностью, включая тесты из её описания. Ничего сверх описания и раздела 1.3 ТЗ.
4. Локально: `pnpm lint && pnpm typecheck && pnpm test` (и `pnpm e2e`, если задача трогает интерфейс). Если задача видимая — запусти игру и проверь в браузере.
5. Самопроверка по разделу «Code Review Rules» ниже и по критериям «Готово, когда».
6. Обнови `docs/progress.md` в той же ветке: статус `done`, заметка к задаче (номер PR, что важно знать дальше), «Заметки для следующей сессии».
7. Коммиты — Conventional Commits на английском. `gh pr create` с описанием «что сделано / решения / как проверить», `gh pr checks --watch`, при зелёном CI — `gh pr merge --squash --delete-branch`. Красный CI — чини, не обходи.
8. Если задача **закрыла веху** — выполни «Конец вехи». Иначе: `Состояние: continue` и короткое сообщение автору: «T-23 готова (PR #12). Следующая — T-24.» Закончи сессию.

## Конец вехи: остановка и отчёт

Когда все задачи вехи `done`:

1. Собери сборку и пройди демо вехи из ТЗ (раздел 8): всё ли работает так, как обещано.
2. Напиши отчёт **`docs/reports/M0.md`** (номер вехи) по шаблону ниже. Источники: `docs/progress.md`, записи этой вехи в `docs/decisions.md`, описания слитых PR, `git log` и `git diff --stat` от тега прошлой вехи (для первой — от первого коммита).
3. Добавь короткую запись в `docs/changelog.md`.
4. Установи `Состояние: milestone-done`, в «Ждёт автора» — «Посмотреть отчёт docs/reports/M0.md и демо».
5. Слей это отдельным PR `report-m0`, затем поставь тег `m0` на `main` и запушь его.
6. **Остановись.** Последнее сообщение автору — краткая выжимка отчёта (5–10 строк) и путь к файлу. Следующую веху не начинай, пока автор не ответит и не вернёт `Состояние: continue`.

**Шаблон отчёта по вехе:**

```markdown
# Отчёт: веха M0 — <название>

Дата · задачи: T-01…T-04 · PR: #1–#5 · коммиты: <первый>..m0

## Коротко
2–4 предложения: что теперь умеет игра и всё ли получилось.

## Как посмотреть
Команды запуска и что попробовать (по шагам) — то самое демо вехи.

## Что сделано
| Задача | Результат | PR |

## Решения, принятые по ходу
Из docs/decisions.md за эту веху: вопрос → решение → почему. Отдельно — **отступления от ТЗ**, если были.

## Изменённые файлы
По областям (core, client, tools, data, docs): что добавлено и изменено. Сводка `git diff --stat`. Новые зависимости и зачем.

## Качество
Тесты (сколько, что покрыто), производительность и размер сборки (если применимо), известные проблемы и технический долг.

## Советы и риски на следующую веху
Что учесть, что может пойти не так, что предлагаешь изменить в плане.

## Вопросы к автору
Что нужно решить, с вариантами и твоей рекомендацией. Если вопросов нет — так и написать.
```

## Состояние в `docs/progress.md`

В шапке файла строка `**Состояние:** <значение>` — по ней автор (и скрипт `scripts/agent-loop.ps1`) понимает, продолжать ли:

| Значение | Когда | Что дальше |
|---|---|---|
| `continue` | Задача сделана, веха не закончена | Новая сессия берёт следующую задачу |
| `milestone-done` | Веха закончена, отчёт написан | Ждём автора |
| `needs-author` | Нужен ответ или работа автора (список ниже) | Ждём автора; вопрос — в «Ждёт автора» |

Значение `continue` после паузы ставит автор (или ты — по его прямой просьбе в чате).

## Когда остановиться и позвать автора

Установи `Состояние: needs-author`, запиши вопрос в «Ждёт автора» и закончи сессию, если:

- нужен доступ, секрет, аккаунт или личные данные (имя для лицензии, адрес VPS и т. п.);
- документы противоречат друг другу, или по формуле получается явно плохое ощущение от игры;
- нужно нарушить жёсткое правило, поменять архитектуру или добавить зависимость в `core`;
- задача не получается после двух разных подходов;
- нужна работа автора: выбор стиля графики, заказ картинок в мастерской, плейтест;
- команда требует прав, которых у тебя нет в песочнице (например, сеть или запись вне репозитория).

Спрашивай кратко: контекст, варианты, твоя рекомендация. Если есть другая незаблокированная задача, не зависящая от ответа, можно оставить `continue` и записать вопрос в «Ждёт автора» — тогда отметь заблокированную задачу как `blocked`.

**Решай сам** и записывай в `docs/decisions.md`: технические детали, которых нет в документах (имена, структура модулей, выбор небольшой библиотеки для клиента или инструментов). Формат: дата, задача, вопрос, решение, почему.

## Жёсткие правила

- **Слои** (ТЗ 2.3): `core` не знает про DOM, Phaser и Preact. Линтер это проверяет — не отключай правила.
- **Детерминизм** (ТЗ 2.4): в `core` нет `Math.random`, `Date`, таймеров; случайность — только через потоки PRNG; состояние меняет только `step`; деньги и количества — целые.
- **Тексты для игрока** — только через ключи локализации (`locales/ru`). **Графика** — только через ключи манифеста ассетов.
- **Числа баланса** — в `data/*.json` / `balance.json`, не в коде.
- **Никаких секретов** — публичный репозиторий: ни ключей, ни паролей, ни адресов серверов, ни личных данных. Локальные настройки — в `.env*`, логи агента — в `.agent-logs/`; оба в `.gitignore`.
- **Документы в `docs/design/` не меняй сам.** Нашёл ошибку или противоречие — предложи правку автору.
- Не делай `git push --force` в `main`, не переписывай историю `main`.
- **Phaser 4** — версия закреплена; сверяйся с документацией именно Phaser 4 (примеры в интернете в основном для Phaser 3). Проблема версии не решается больше дня — можно перейти на Phaser 3 с записью в `docs/decisions.md`.

## Работа на компьютере автора

- Работай только внутри папки репозитория. Не трогай файлы вне её.
- Не устанавливай ничего глобально без спроса. pnpm — через `corepack enable`.
- Автор работает на **Windows**: все скрипты в `package.json` и `tools/` — кроссплатформенные (Node.js), без bash-синтаксиса. Если нужен скрипт оболочки — сразу две версии: `.sh` и `.ps1`.
- Долгие процессы (`pnpm dev`) не оставляй висеть: для автотестов сервер поднимает Playwright, для ручной проверки — запусти, проверь, останови.

## Как держать `docs/progress.md` коротким

Только текущее состояние, не история: шапка (этап, веха, состояние), таблица задач текущего этапа, «Заметки для следующей сессии» (не больше 15 строк) и «Ждёт автора». Подробности — в PR, `docs/decisions.md` и отчётах.

## Code Review Rules

Правила для автоматического ревью PR (например, Codex code review на GitHub) и для самопроверки. Форматирование и линтер проверяет CI — здесь только смысл.

- **Детерминизм ядра.** В `packages/core` нет `Math.random`, `Date`, `performance`, таймеров, DOM, импортов из `client`; состояние меняется только внутри `step`; случайность — только через потоки PRNG состояния. Безопасный путь: передать значение командой или взять из потока PRNG.
- **Целые деньги.** Серебро, количества товаров, провизия и матросы — целые числа; деление — с явным `round`/`floor` по формуле из ТЗ.
- **Совпадение с ТЗ.** Формулы и константы совпадают с ТЗ этапа или вынесены в `data/*.json`; «тихие» изменения формул — ошибка.
- **Тексты и графика.** В интерфейсе нет строковых литералов для игрока (только ключи локализации) и путей к картинкам (только ключи манифеста).
- **Сохранения.** Изменение формы состояния сопровождается поднятием `schemaVersion` и миграцией; старые сохранения из `test/golden-saves` загружаются.
- **Секреты.** В коде, конфигах и истории нет ключей, паролей, адресов серверов и личных данных.
- **Тесты.** Каждый пункт «Тесты» из описания задачи покрыт; тест детерминизма не «чинится» обновлением эталона без объяснения в PR.
